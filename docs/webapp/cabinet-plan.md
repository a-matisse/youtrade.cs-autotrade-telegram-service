# Кабинет Y.CS: рабочий план

Черновик для согласования. OAuth и новый кабинет пока не подключены.
Контракт входа: [Telegram OIDC](../external-patches/lis-tm/7/web-auth-frontend.md).

## Зафиксированные требования

- Один профиль Y.CS с доступом через сайт и Telegram.
- В первой версии добавляется вход через Telegram; основные действия остаются
  в боте. Веб-функции появляются по мере реализации, без обещания готовности
  отсутствующих разделов.
- На телефоне кабинет ориентирован на статистику, графики и короткие сводки.
- Работа с таблицами предназначена для ПК. Таблицы отображаются и редактируются
  прямо на сайте, изменения отправляются backend в JSON.
- Обмена таблицами через файлы, включая импорт и экспорт Excel/CSV, в кабинете
  не будет. Пользователю не нужно переносить файлы между сайтом и компьютером.
- Единственное запланированное исключение для загрузки файла — maFile при
  добавлении Worker. Сам сценарий добавления пока не реализуется.
- Работа существующего Telegram-интерфейса и его таблиц этим планом не меняется.

## Предложения по входу и CTA — на согласование

- Справа сверху: «Войти» со значком Telegram; после входа — «Кабинет».
- Первый экран: основная кнопка «Начать работу» ведёт ко входу на сайте,
  вторая «Открыть бота» ведёт в Telegram.
- «Как это работает» остаётся отдельной текстовой ссылкой.
- После входа кабинет показывает готовые функции и заметный переход в бота.
  Пояснение первого этапа: «Настройка торговли и управление аккаунтами доступны
  в Telegram».
- На телефоне табличные разделы не занимают основную навигацию. Прямая ссылка
  открывает пояснение о доступности работы с таблицами на компьютере и возврат
  к обзору. Поведение для планшетов ещё нужно согласовать.

## Что нужно уточнить в backend до подключения OAuth

Действующий backend разрешает вход существующему пользователю Y.CS. Новый
пользователь получает 403 с предложением сначала запустить бота. Для старта
через сайт потребуется отдельное согласование создания профиля.

Нужно различать подтверждённую Telegram-идентичность и факт запуска бота.
OAuth-вход сам по себе не означает, что бот уже может взаимодействовать с
пользователем. Обязательный редирект на `/connect-bot` в старом frontend
потребуется пересмотреть вместе с этим контрактом.

Старые iframe Telegram Login Widget и `/auth/telegram` заменяются OIDC flow
из документа. Access хранится в памяти, refresh — в серверной HttpOnly cookie.
Нужны восстановление сессии, единое обновление credentials для параллельных
запросов и вкладок, выход и понятные ошибки. Кабинет использует web API,
а не внутренние Telegram-маршруты с сервисным ключом.

## Экран первого запуска приложения

Реализуется отдельно от OAuth: стартовый HTML содержит скрытый экран Y.CS с
линейным индикатором. Маленький script `/app-loader.js` работает до загрузки
основного bundle; `AppReady` сообщает о первой отрисовке React.

- При холодном запуске экран является первым видимым состоянием: лендинг
  не показывается перед ним. Фон появляется сразу, содержимое плавно
  проявляется за 280 мс. После готовности React экран растворяется в приложении
  за 380 мс. Быстрый холодный запуск завершает анимацию появления перед уходом,
  поэтому экран не вспыхивает на один кадр.
- До показа выполняется локальная проверка HTTP-кэша через `only-if-cached`,
  без сетевого запроса. Сборка передаёт загрузчику точное имя текущего bundle.
  При попадании в кэш экран пропускается; Resource Timing дополнительно
  проверяет фактическую загрузку. Сессионный флаг «сайт уже открывали» не
  используется: он не подтверждает наличие актуального приложения в кэше.
- При полной перезагрузке JavaScript выполняется заново. При подтверждённом
  попадании основного bundle в кэш пропускаются и экран, и входная анимация.
- Переходы внутри React-приложения, обновление статистики, запросы API и
  загрузка изображений не запускают этот экран.
- Без JavaScript экран остаётся скрытым, пререндеренный лендинг доступен.
- При ошибке запуска или ожидании дольше 30 секунд доступно ручное обновление.
- Учитываются выбранная тема и `prefers-reduced-motion`. Проценты загрузки
  не имитируются: полоса обозначает ожидание и завершается при готовности UI.

Дальнейшая реализация OAuth и кабинета начинается после согласования плана.
