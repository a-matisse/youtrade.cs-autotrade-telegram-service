# Реферальный кабинет и оферта: разбор новых контрактов

Дата: 2026-09-17. Источники: [реферальный баланс](../external-patches/lis-tm/2/frontend-referral-balance-2026-09-17.md), [оферта](../external-patches/lis-tm/2/frontend-service-terms-2026-09-17.md). Реферальный кабинет, перевод, инструкция по выплате и прогресс бонуса реализованы в клиенте; команда документов остаётся отдельным следующим этапом.

## Уточнённый сценарий продукта

По информации владельца, QuickConfig уже подготовлен сервером. Пользователь один раз настраивает торговлю/включает баргейны, затем в основном добавляет аккаунты, проверяет полноту их списка, смотрит ожидание и историю продаж. Переименование/удаление редки, углублённые настройки почти не используются. Обязательный мастер настройки не является приоритетом. Новые документы и рефералка не должны усложнять этот рабочий путь.

## Реферальный кабинет

Подтверждено контрактом:

- `balance` — основной баланс; `referralBalance` — доступное реферальное вознаграждение. Для оплаты сервиса их нельзя складывать до явного перевода.
- `totalReferralEarnings` — заработано за всё время, не доступная сумма. `totalDeposits` — личные пополнения.
- GET `/api/telegram/user/ref/balance?chatId=...` возвращает балансы и статистику.
- POST `/api/telegram/user/ref/balance/transfer` принимает `chatId`, `amount`, `requestId`. Перевод 1:1, без комиссии и бонуса пополнения.
- После POST показывать балансы из ответа. При неизвестном результате повторять исходный запрос с тем же UUID и суммой, не создавать новый UUID.
- Отсутствующее поле referralBalance при поэтапном развёртывании означает ноль. Ошибка запроса не означает нулевой баланс.
- Внешний вывод выполняет администратор: endpoint сразу списывает деньги и возвращает COMPLETED, а фактическую отправку выполняет оператор вручную. COMPLETED здесь не доказывает получение денег пользователем.

Предлагаем оставить вход со старта и `/referral`. Первый экран:

```text
Реферальный кабинет

Доступно: $35.00
Заработано за всё время: $85.00

Ваша ссылка: …
Условия вознаграждения: …

[Пригласить друга]
[Перевести на баланс сервиса]
[Как получить выплату]
[Назад]
```

Цифры иллюстративные, из примера API. Основной баланс показывать отдельно, в том числе на экране перевода. Оборот и totalDeposits не делать главными показателями кабинета без отдельной пользовательской задачи. Бонус приглашённому и процент владельцу кода не смешивать с заработком и доступным балансом.

Перевод: «Всю сумму» / «Указать сумму» → подтверждение суммы и условий → результат. Использовать BigDecimal. Повторные нажатия относятся к той же операции. UUID и неизменяемые параметры сохранять до отправки устойчиво к перезапуску: существующие registry в памяти не обеспечивают такое восстановление.

«Как получить выплату» — инструкция и переход к поддержке, если владелец подтвердит процесс. Пользовательского API заявки/адреса/сети в документе нет. Административное списание не вызывать из пользовательской кнопки. $1 — комиссия по умолчанию, администратор может задать другую целую сумму; не обещать фиксированную комиссию.

В параметре amount административного вывода написано «резервируется», но дальнейшее описание явно говорит о немедленном списании без отмены. Это неоднозначность текста документа; проектировать интерфейс следует с учётом явно описанного списания.

Для приглашения есть обработчик `/start promo_...`; нужны username бота и проверка формата реальных кодов. Новый документ не предоставляет счётчик приглашённых или историю начислений.

## Документы и согласия

Предлагаемая команда `/documents` — «Документы и согласия», без новой кнопки на рабочем экране.

Путь: команда → общая оферта и статус её текущей версии → полный текст → «Принять версию …» → серверное подтверждение. Принятую старую версию не выдавать за принятие текущей.

- Тип общей оферты: `YCS_SERVICE_TERMS`.
- GET `/api/telegram/user/p2p/documents?chatId=...` возвращает документы.
- POST `/api/telegram/user/p2p/document-acceptances?chatId=...`: заголовок `Idempotency-Key`, JSON с type/version/contentHash из GET. Сохранить существующий X-Service-Key.
- Для оферты UUID передаётся заголовком, для перевода — параметром requestId: контракты различаются.
- Не пересчитывать hash после преобразования текста. Кнопка связана с показанной версией/хешем; нельзя автоматически принимать обновлённый документ старой кнопкой.
- Полный Markdown нужно предоставить без обрезания; длинный текст разбивать на читаемые части, при необходимости давать исходный файл. Совместимость с Telegram MarkdownV2 нельзя предполагать автоматически.
- В примере published=false, ниже сказано, что общая оферта всегда published=true. Учитывать фактический флаг: для черновика не показывать принятие.
- Общая оферта сейчас добровольная, не блокирует торговлю. P2P-документы публикуются независимо.
- Историю согласий читать с сервера, локального boolean недостаточно.

## Bargain

Публичный доступ не включает режим торговли. Выдача/продление доступа выполняется ежечасной задачей: новичок потенциально может некоторое время иметь bargainAllowed=false. Показывать фактическое состояние сервера, не обещать мгновенный доступ. Нового переключателя публичного доступа в боте не требуется.

## Точки изменений клиента

- FcdGeneralAccInfoDto, FcdParamsGetDto, FcdParamsListDto и YTBalanceNotification: referralBalance и раздельное отображение средств.
- FcdRefDto: totalReferralEarnings; новые DTO балансов/операции и методы RefEndpoint.
- UserRefState/UserRefMenu: новая сводка и действия, подтверждение перевода, устойчивый учёт requestId.
- Новый клиент документов/принятий, DTO и состояния, команда в UserMenu. В текущих Java-исходниках интеграция document-acceptances не найдена.
- В предупреждении о низком основном балансе можно предложить перевод доступного реферального вознаграждения; не переводить автоматически.

## Что уточнить перед реализацией

1. Полные JSON ответа Acceptance и GET истории согласий, включая корневую структуру и даты.
2. Корневая структура новых balance/transfer: примеры показывают голые объекты, существующий RefEndpoint использует FcdDefaultDto.
3. HTTP-статусы и тела ошибок: недостаток средств, неверная сумма, UUID с другими параметрами, устаревшая версия/хеш, повторное принятие.
4. Срок хранения идемпотентных результатов и способ сверки неизвестного результата. Повтор POST с тем же ключом описан, отдельный GET операции не указан.
5. Минимальная сумма перевода и точность входа: примеры в центах, границы валидации не перечислены.
6. Процесс ручной выплаты: контакт, необходимые данные, подтверждение фактической отправки. Не придумывать срок и способы выплаты.

Это вопросы корректности реализации крайних случаев, а не препятствие для обсуждения расположения элементов.
