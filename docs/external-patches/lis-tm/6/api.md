# Контракт Balance Market

Ниже — проект **собственного API Y.CS**. Маршруты, формы ответа и допустимые статусы будут утверждены после уточнения RedBalance и котировки. Существующие `/api/.../market-csgo/money-send` и `/balance-transfer` — тоже API Y.CS, но они выполняют отдельные пользовательские операции, а не сессию вывода.

HTTPS шифрует и путь с query, и JSON body при передаче. Для сумм, адреса и пароля предпочтителен `POST` с JSON body: URL чаще сохраняется в access logs, истории браузера и трассировках. Body тоже нельзя считать защищённым от логирования автоматически: на наших контроллерах, прокси и APM нужно исключить запись секретов.

## Два пользовательских канала

Для Balance Market обязательны **оба самостоятельных контракта: web API и Telegram API**. Все пользовательские действия доступны и на сайте, и через кнопки Telegram-бота: выбор своего аккаунта Market.CS, выбор способа вывода, ввод суммы и реквизитов, получение котировки, подтверждение заявки, просмотр активной заявки и её статуса, отмена до принятия worker-ом. Оба входных контроллера вызывают один application service и возвращают одинаковые расчёт, ограничения, публичные статусы и причины ошибок. Различается только способ установления личности: web использует свою авторизацию, Telegram API использует существующий доверенный backend бота и привязку к пользователю. Бот не вызывает web endpoint от имени пользователя.

Точные Telegram-префикс, формат авторизации и DTO сверить с действующими Telegram-контроллерами перед реализацией. Для платёжного пароля использовать существующий в боте сценарий Market.CS: принять текстовое сообщение, сразу удалить его из чата, держать значение только на время операции и очистить после отправки. Кнопки бота ведут по всем этапам и показывают результат; секреты не попадают в callback data, Redis и ответы API.

## API приложения

`POST /api/web/v1/balance-market/quote` с JSON body принимает ID собственного аккаунта, сумму Market.CS к списанию и код способа вывода. Этот запрос только рассчитывает и сохраняет котировку, денег не переводит. Текущий ответ пользовательских web и Telegram ручек обёрнут в FCD: `result`, `cause`, `data`; содержимое котировки или заявки лежит в `data`. Пример тела:

```json
{"accountId": 123, "amount": "1000.00", "withdrawalMethod": "USDT_TRC20"}
```

Ответ содержит ID котировки, курс продавца, время его обновления, курс клиента, ставку надбавки, сумму Market.CS, сумму USDT, точность/округление, срок действия и доступность. Telegram API обязательно возвращает ту же котировку для экрана подтверждения в боте. Котировка не содержит `rb_session`, платёжного пароля и API-ключей.

`POST /api/web/v1/balance-market/sessions` с JSON body принимает ID подтверждённой котировки, ID собственного аккаунта, сумму Market.CS к списанию, `withdrawalMethod`, полный адрес и платёжный пароль; ключ идемпотентности передаётся отдельным заголовком. Сервер проверяет владение аккаунтом, свежесть курса, допустимость способа вывода, сумму, согласие с адресом и отсутствие другой активной заявки на этот аккаунт. При создании сохраняет снимок курса с `rateUpdatedAt` и денежными суммами, ставит заявку в очередь и сразу возвращает её ID, `status=QUEUED`, `canCancel=true` и `queueExpiresAt` через 15 минут. Внешние переводы в этом HTTP-запросе не выполняются. Пароль не возвращается ни в одном ответе.

Последний сохранённый курс допустим, если его возраст не превышает 1 минуту и последняя попытка обновления была успешной. Курс обновляется каждые 30 секунд. Старый курс или неуспешное последнее обновление возвращают явную ошибку до денежного старта; прежний успешный ответ не используется как fallback. Сохранённые для заявки курс и сумма USDT не пересчитываются фоновым обновлением.

Справочник способов вывода должен возвращать серверный enum с человекочитаемой меткой. В первой версии единственное значение — `USDT_TRC20` с меткой «USDT TRC-20»; в приложении оно отображается отдельной кнопкой. Новые значения добавляются без изменения структуры заявки.

`GET /api/web/v1/balance-market/sessions/{id}` возвращает только принадлежащую пользователю заявку: `status`, текущий `stage`, `canCancel`, `queuedAt`, `queueExpiresAt`, `acceptedAt`, `updatedAt`, суммы, способ вывода, маскированный адрес для списка и полный адрес на защищённом экране деталей, подтверждённый внешний результат и публичный код причины остановки без секретов. При автоотмене это `status=CANCELLED`, `reason=QUEUE_TIMEOUT`. Сайт и Telegram-бот перечитывают состояние через свои пользовательские API после reconnect. Повторное создание с тем же Idempotency-Key и тем же телом возвращает ту же заявку.

`GET /api/web/v1/balance-market/sessions/active` возвращает текущие незавершённые заявки авторизованного пользователя, чтобы после открытия приложения показать уже стоящую в очереди заявку и доступную кнопку отмены. ID пользователя берётся из авторизации, query-параметры с его данными не нужны.

`POST /api/web/v1/balance-market/sessions/{id}/cancel` принимает JSON body с необязательной причиной пользователя и Idempotency-Key. Если заявка всё ещё `QUEUED`, сервер атомарно переводит её в `CANCELLED`, удаляет временный платёжный пароль и возвращает обновлённую публичную проекцию. Если worker уже принял заявку, сервер возвращает конфликт состояния с актуальными `status`/`canCancel=false`; кнопку больше не показывать. Повтор отмены `CANCELLED` возвращает тот же итог.

Telegram API обязателен для всего пользовательского пути. Нужны операции: список доступных собственных Market.CS аккаунтов или ссылка на действующий Telegram API аккаунтов; справочник способов вывода; котировка; создание заявки; чтение заявки по ID и активной заявки; отмена. Они возвращают те же DTO и ошибки, что web API, и вызывают тот же application service. Redis Stream отправляет событие о постановке в очередь, принятии, отмене и завершении; после события бот перечитывает заявку через Telegram API. При `QUEUE_TIMEOUT` бот показывает причину автоотмены. Точные маршруты утвердить после сверки с существующим Telegram API.

| Действие пользователя | Web API | Telegram API и бот |
| --- | --- | --- |
| Выбрать свой аккаунт Market.CS | Существующий API аккаунтов либо новый Balance Market список | Существующий Telegram API аккаунтов либо новый список; кнопка выбора |
| Выбрать способ вывода | Справочник `withdrawalMethod` | Тот же справочник; кнопка «USDT TRC-20» |
| Указать сумму и увидеть курс, комиссию, USDT | `POST /quote` | Отдельный Telegram `POST /quote`; экран котировки |
| Ввести адрес, пароль и подтвердить заявку | `POST /sessions` | Отдельный Telegram `POST /sessions`; сообщение с паролем бот сразу удаляет по действующему образцу Market.CS |
| Увидеть уже активную заявку | `GET /sessions/active` | Telegram `GET /sessions/active`; кнопка перехода к заявке |
| Получить состояние и итог | `GET /sessions/{id}` | Telegram `GET /sessions/{id}`; экран статуса и уведомления |
| Отменить до принятия worker-ом | `POST /sessions/{id}/cancel` | Telegram `POST /sessions/{id}/cancel`; кнопка только при `canCancel=true` |

В таблице пути сокращены относительно префикса канала; Telegram-пути проектные, пока не утверждённые. Ответы обоих API содержат одинаковый `sessionId`, суммы, зафиксированную комиссию, `status`, `stage`, `canCancel`, времена и публичный код причины. Идемпотентность создания и отмены действует на пользователя и действие независимо от канала: повтор после потери ответа не создаёт новую заявку.

Если для площадки не назначен отдельный аккаунт остатков, создание денежной сессии возвращает стабильную пользовательскую ошибку `REMAINDER_ACCOUNT_NOT_CONFIGURED` без вызова `money-send`. Backend пишет один короткий диагностический лог с типом площадки и ID попытки, без секретов и повторяющегося stack trace.

### Debug API: рабочая секция Balance Market

Для ручной выплаты при `youtrade.balance-market.auto-payout=false` используются `GET /api/debug/balance-market/sessions/{id}/payout-approval` (несекретные данные заявки для сверки) и `POST` по тому же пути с JSON `{"redBalanceOrderId":"RBX-..."}`. Подтверждение допустимо только для `status=PROCESSING`, `stage=WAITING_FOR_PAYOUT_APPROVAL` и совпадающего ID заказа; после него worker продолжает исполнение. Повторное подтверждение возвращает `409`. При `auto-payout=true` новые заявки переходят к выплате сразу после `funded`; ранее остановленные заявки остаются на ручном подтверждении.

Swagger-раздел `Balance Market · Configuration` объединяет настройки аккаунтов и `rb_session`. Маршруты:

| Действие | Метод и маршрут | Результат |
| --- | --- | --- |
| Добавить управляющий аккаунт | `POST /api/debug/balance-market/managing-accounts` | Создаёт запись, возвращает ID и несекретные метаданные |
| Заменить реквизиты аккаунта | `PUT /api/debug/balance-market/managing-accounts/{id}/credentials` | Обновляет `login`, `password` и maFile JSON существующей записи |
| Платёжный пароль управляющего аккаунта | `PUT /api/debug/balance-market/managing-accounts/{id}/payment-password` | Сохраняет пароль для переводов |
| Просмотреть или удалить управляющий аккаунт | `GET /api/debug/balance-market/managing-accounts`, `DELETE /api/debug/balance-market/managing-accounts/{id}` | Список без реквизитов; удаление только если запись не используется |
| Добавить аккаунт остатков | `POST /api/debug/balance-market/remainder-accounts` | Создаёт отдельную запись получателя остатков |
| Изменить аккаунт остатков | `PUT /api/debug/balance-market/remainder-accounts/{id}` | Меняет назначение и настройки получателя остатков |
| Просмотреть или удалить аккаунт остатков | `GET /api/debug/balance-market/remainder-accounts`, `DELETE /api/debug/balance-market/remainder-accounts/{id}` | Список без API-ключей; удаление только если запись не используется |
| Задать `rb_session` | `PUT /api/debug/balance-market/redbalance/session` | JSON `{"rbSession":"..."}`; cookie не возвращается; при `REFRESH` обновляет cookie приостановленной заявки и возобновляет её |
| Просмотреть или удалить `rb_session` | `GET /api/debug/balance-market/redbalance/session`, `DELETE /api/debug/balance-market/redbalance/session` | Возвращает только признак настройки и состояние курса; удаление запрещено при активной выплате |
| Посмотреть кэш курса | `GET /api/debug/balance-market/redbalance/rate` | Текущая ставка и время обновления без cookie |

Создание и замена реквизитов принимают `multipart/form-data` с двумя частями: `data` — JSON с реквизитами (`Content-Type: application/json`), `maFile` — текстовый файл (`Content-Type: text/plain`). При создании `data` содержит `market`, `displayName`, `login`, `password`, `proxy`, `enabled`, `priority`; при замене — `login`, `password`, `proxy`. Содержимое `maFile` не нужно копировать в `data`: файл выбирается отдельно. Сервер читает его текст как UTF-8, затем разбирает содержащийся JSON и сохраняет компактную строку. Пробелы и переносы в тексте файла допустимы, включая неэкранированные управляющие символы внутри строк. Замена реквизитов требует все четыре значения, включая файл. ID записи генерирует БД.

Ответы по управляющему аккаунту содержат только `id`, `market`, `displayName`, `enabled`, `priority` и `updatedAt`. Запросы доступны только администратору через debug API; body, значения реквизитов, полный maFile и строку proxy не логировать и не включать в аудиторские события. По решению владельца реквизиты аккаунта сохраняются в этой таблице без шифрования; это не означает, что их можно возвращать через API. Аккаунты, на которые уже ссылаются заявки или операции выпуска ключа, БД удалить не даст: API возвращает `409`.

Для `balance_market_remainder_account` создание принимает `market`, `youtradeSteamTokenId`, `enabled`, `priority` согласно [проекту схемы](data-model.md). Изменение принимает тот же набор полей и выполняется по внутреннему ID записи; отсутствующие поля не должны неявно стирать существующую конфигурацию. `youtradeSteamTokenId` должен указывать на существующий `YouTradeSteamToken` Y.CS со связанным активным `marketSellToken`. Отображаемое имя в административном ответе берётся из `YouTradeSteamToken.getDisplayName()`, ключ получателя `money-send` — из `YouTradeMarketSellToken.apiKey`. В ответе можно показать ID связанного токена продажи, но не сам API-ключ. Создание либо изменение не меняет маршрут уже принятой заявки. При отсутствии настроенного аккаунта остатков денежный запуск запрещён.

Для обеих ролей предусмотреть чтение списка записей и явное включение/отключение через тот же debug API, чтобы администратор мог проверить настройку и вывести аккаунт из новых назначений. Один и тот же фактический аккаунт нельзя назначить одновременно управляющим и остаточным; способ проверки этого условия уточнить после контракта реквизитов аккаунта остатков.

Настройка cookie не делает старый курс актуальным: новая котировка доступна только после следующего успешного запроса курса с этой сессией. Замена cookie при активной выплате разрешена только в состоянии `REFRESH` или `VERIFYING`; удаление запрещено. При HTTP `401` от `/api/me` cookie получает `sessionStatus=REFRESH`, курс становится недоступным, а связанная заявка — `status=PAUSED`, `reason=REDBALANCE_SESSION_REFRESH_REQUIRED`. Связь с заявкой сохраняется: другую выплату нельзя запустить. После замены cookie переходит в `VERIFYING`, и заявка остаётся на паузе до успешной проверки `/api/me` и обновления курса. Только затем заявка получает новую копию cookie и продолжает с сохранённой стадии; повтор создания заказа или intent разрешён только после явного `401`. Пользовательские web и Telegram API возвращают `PAUSED` и причину в обычном DTO заявки.

### Debug API: тестовая секция Balance Market

Swagger-раздел `Balance Market · Tests` содержит `GET /api/debug/balance-market/test/state` со статусом provisioning и состоянием курса без секретов. Запросы `GET .../test/redbalance/me`, `/rates` и `/orders` выполняют реальные запросы к RedBalance с настроенным `rb_session` и возвращают внешний HTTP-статус, `remoteStatus`, `message` и JSON-ответ. `POST .../test/redbalance/orders/{orderId}/check` позволяет проверить ответ `awaiting_transfer`/`funded` для существующего заказа. `DELETE .../test/redbalance/wallet` отправляет `PUT /api/me/wallet` с пустым адресом; `PUT .../test/redbalance/wallet` принимает JSON `{"address":"<TRC-20>"}`. **Все ручки тестовой секции возвращают `409`, если есть незавершённая заявка на вывод, включая очередь (`QUEUED`).** Изменение кошелька дополнительно требует выключенного provisioning. Раздел не создаёт заявки и не выполняет `payout`. Все ответы имеют `Cache-Control: no-store`; cookie не возвращается.

API доставки нового ключа управляющего аккаунта в Y.CS нет. Userbot получает принятую заявку из общей PostgreSQL и через JPA атомарно обновляет её строку: `managing_api_key` (ключ открытым текстом), `api_key_received_at`, `stage=API_KEY_READY`, `updated_at` и версию. Предусловия — `status=PROCESSING`, `stage=WAITING_FOR_API_KEY`, совпадение `managing_account_id` и связь с активной RedBalance-сессией. Реквизиты исходного аккаунта администратор по-прежнему задаёт через debug API; это отдельная операция. См. [ТЗ userbot](marketapp-key-provisioning/README.md).

Подтверждённая выплата публикуется в существующий Redis Stream `notification-stream` как `type=BALANCE_MARKET_PAYOUT`. Payload содержит `sessionId`, `tdId`, `chatId`, исходную и выплаченную суммы, метод, адрес кошелька, ID заказа и доступные реквизиты выплаты. В этом контракте нет `eventId`: получатель дедуплицирует выплату по `sessionId` и после reconnect перечитывает заявку по API. Событие не содержит API-ключи, пароль, cookie, необработанные ответы RedBalance и полный URL Market.CS. Схема payload: [уведомление о выплате](../patches/balance-market-payout-notification.md).

## Внешние адаптеры

- **Наш API** принимает `accountId` и сумму от пользователя, создаёт котировку/сессию и возвращает её статус. Наш backend сам находит API-ключ выбранного пользовательского Market.CS аккаунта. Пользователь не передаёт этот ключ в JSON формы вывода.
- **Market.CS API** вызывается сервером через `MarketCsgoMoneyTransferClient`: `get-money` для баланса и `money-send` для подтверждённых переводов. После принятия заявки внешний marketapp через Playwright выпускает новый API-ключ управляющего аккаунта и вместе с переходом в `API_KEY_READY` записывает его в общую БД; только затем Y.CS очищает прежний баланс и переводит средства пользователя на этот ключ. При переводе клиента отправитель — его выбранный аккаунт и его платёжный пароль. Для начальной очистки и конечного остатка отправителем выступает управляющий аккаунт, получателем — закреплённый аккаунт остатков. Роль Market.CS `money-send` после `POST /api/orders` ещё не подтверждена. Существующий сервис сбора денег между аккаунтами — пример механики вызова, а не готовый оркестратор сессии.
- Курс RedBalance: `rb_session` хранится как серверный секрет и передаётся только сервером. Получены примеры `GET https://redbalance.trade/api/me` и `GET https://redbalance.trade/api/rates`, подробно описанные в [контракте RedBalance](redbalance-api.md). Для неавторизованного запроса передан HTTP `401` с JSON `{"error":"unauthorized","message":"Войдите через Telegram"}`. Такая попытка переводит cookie в `REFRESH`, приостанавливает связанную заявку, а создание новой блокируется до восстановления сессии и успешного обновления курса. Применимость персональной ставки, срок жизни cookie и единицы расчёта пока требуют подтверждения.
- Особенность внешнего Market.CS API: существующий клиент вызывает `money-send/{amount}/{recipient_key}` с `key` и `pay_pass` в URL; `amount` для USD сейчас передаётся в тысячных доллара. JSON body нашего API не меняет контракт Market.CS. Поэтому полный URL внешнего вызова нельзя логировать, сохранять в ошибках или передавать в APM. Клиенту сессии требуется безопасный журнал исходов и сверка перед повтором.
- RedBalance: после сброса/установки кошелька через `PUT /api/me/wallet` и сверки `GET /api/me` из подтверждённого поступления на управляющий аккаунт удерживаются **наши 0,2%**. Остаток без нашей комиссии передаётся как `amount` в `POST /api/orders` вместе с `marketApiKey` управляющего аккаунта. Ответ содержит `id`, `status=awaiting_transfer`, `expected`, `expiresAt` и `recipientKey`. Затем `POST /api/orders/{id}/intents` с **тем же amount** возвращает `customId`, `amountUnits`, `recipientKey` и `transferUrl` вида `https://market.csgo.com/api/v2/money-send/{amountUnits}/{recipientKey}?key={managingAccountApiKey}&custom_id={customId}`. После сверки сервер вызывает существующий `MarketCsgoMoneyTransferClient.send` с полями intent, платёжным паролем управляющего аккаунта и `customId`; клиент сам строит GET. `POST /api/orders/{id}/check` подтверждает поступление при `funded`; фактическая выплата берётся из ответа `check` и может отличаться от предварительной котировки. Затем `POST /api/orders/{id}/payout` отправляет USDT. Прямой успешный ответ содержит оба статуса `paid`, совпадающие ID и сумму и непустой `txid`. При неизвестном исходе payout сверяться через `GET /api/orders` по ID и `rawStatus=paid`; этот список отсортирован от новых заявок к старым, но не содержит `txid`. Оба варианта позволяют отметить выплату отправленной, но при восстановлении `txid` остаётся неизвестным. См. [контракт RedBalance](redbalance-api.md).

Для сайта `youtradecs.xyz` нужен общий серверный API котировки с той же ставкой `youtrade.balance-market.markup-rate`. Отдельного коэффициента во фронтенде или другом backend не должно быть. Формулу публикации курса нельзя закрепить до ответа на [вопросы](open-questions.md).

В ответе котировки также нужны `redBalanceFeePercent`, `youtradeFeePercent`, `totalFeePercent`, `networkFeeUsd`, денежные суммы процентных удержаний, расчётная выплата и источник применённой ставки. При действующем промо процентные ставки составляют 3%, 0,2% и номинально 3,2%; интерфейс **отдельно** показывает $1.50 сетевой комиссии, которая уменьшает итоговую выплату сверх процента. Backend рассчитывает итог после последовательных удержаний, а фронтенд только отображает его. Ставки и лимит 500–10 000 USD за одну заявку проверяются сервером. При истечении промо итог пересчитывается по подтверждённому правилу, а не остаётся 3,2% автоматически.
### Позиция заявки в очереди

`POST /api/web/v1/balance-market/sessions`, `GET /api/web/v1/balance-market/sessions/active`, `GET /api/web/v1/balance-market/sessions/{id}` и соответствующие Telegram-маршруты `/api/telegram/user/balance-market/sessions` используют одинаковое поле `queueAhead` внутри DTO заявки. Для `QUEUED` оно показывает число заявок перед данной: `0` — следующая, `1`–`3` — точное число, `4` — больше трёх. Выполняемая заявка учитывается в этом числе. После выхода из очереди значение `null`. Поле пересчитывается при каждом чтении заявки, поэтому не является фиксированной позицией или прогнозом времени. Тексты и поведение интерфейса описаны в [контракте фронта](FRONTEND.md).
