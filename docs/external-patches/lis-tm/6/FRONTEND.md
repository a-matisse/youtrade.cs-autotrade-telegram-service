# Balance Market: контракт для сайта и Telegram-бота

Backend — единственный источник курса, комиссий, допустимых сумм и состояний заявки. Сайт и бот показывают полученную котировку, не пересчитывая её самостоятельно. Изменение интерфейса сайта выполняется отдельно после согласования с владельцем.

Текущие web и Telegram API используют общий FCD-контракт: успешный ответ имеет вид `{"result":true,"cause":"success","data":{...}}`, ошибка определения пользователя — `{"result":false,"cause":"...","data":null}`. Данные котировки и заявки находятся в `data`; для `GET /sessions/active` это массив. Ошибки валидации и состояния операции возвращаются HTTP 4xx с `code` и `message`.

## Курс и котировка

После входа пользователь выбирает свой аккаунт Market.CS, способ `USDT_TRC20` и сумму к списанию от 500 до 10 000 USD. Фронт отправляет эти значения в `POST /api/web/v1/balance-market/quote` с JSON body; Telegram использует свой endpoint с тем же содержимым. Ответ должен содержать ID котировки, `rateUpdatedAt`, ставку RedBalance, надбавку Y.CS 0,2%, отображаемую общую процентную ставку, комиссию сети $1.50, сумму Market.CS к списанию, прогноз USDT к получению и время истечения котировки.

До окончания промо ставка RedBalance берётся из `GET /api/me` → `user.promo.rate`. После окончания промо используется текущая ставка `GET /api/rates` → `buy`. Ответ `/api/rates` сам по себе не перекрывает ещё действующее персональное промо. Суммы транзакций округляются **вниз до трёх знаков после запятой** на backend. При недоступном или устаревшем курсе показывать ошибку обновления, а не старую цену как актуальную.

При подтверждении заявки фронт передаёт ID котировки, выбранный аккаунт, сумму, метод, полный адрес кошелька и платёжный пароль. Перед отправкой ещё раз показывает адрес и сеть. Платёжный пароль не сохраняется в браузере и не включается в URL или события аналитики. В Telegram использовать уже работающий порядок: пользователь пишет пароль сообщением, бот сразу удаляет сообщение из чата и передаёт пароль backend для операции.

## Очередь и состояние

Создание заявки сразу возвращает `sessionId`, `status=QUEUED`, `queueExpiresAt` и `canCancel=true`. Экран показывает ожидание и даёт отмену, пока `canCancel=true`. Через 15 минут без принятия worker-ом заявка получает `CANCELLED` и `reason=QUEUE_TIMEOUT`. После принятия worker-ом `canCancel=false`; экран получает текущий `stage` и публичное объяснение задержки либо ошибки. При `WAITING_FOR_PAYOUT_APPROVAL` показать ожидание ручной проверки оператором; пользователь не подтверждает выплату сам. При повторном открытии сайт и бот перечитывают активную заявку с backend. Сообщение об успешной выплате показывается только после подтверждённого `paid` и сохранения результата.

Нужны отдельные web и Telegram запросы для способов вывода, котировки, создания заявки, чтения активной/конкретной заявки и отмены. Оба канала отображают одинаковые суммы и статусы из backend.

## Подтверждение выплаты и уведомление

Сайт получает итог из API заявки: `status=PAID` означает, что RedBalance подтвердил отправку USDT, а `status=COMPLETED` дополнительно означает завершение очистки остатка управляющего аккаунта. Для показа результата использовать `actualPayout`, `walletAddress`, `withdrawalMethod`, `redBalanceOrderId`, `payoutTxid` и `completedAt`; `estimatedPayout` оставлять как исходный прогноз. `payoutTxid` может быть `null`, если выплату подтвердили после таймаута через список заказов RedBalance. Отсутствие TXID в таком случае не отменяет подтверждённую выплату. При `status=PAUSED` и `reason=REDBALANCE_SESSION_REFRESH_REQUIRED` показать, что вывод ожидает обновления авторизации RedBalance оператором; повторно создавать заявку или предлагать отмену нельзя. При `MANUAL_REVIEW` и других неподтверждённых состояниях не показывать сообщение об отправленной выплате.

Backend публикует в `notification-stream` объект с `type=BALANCE_MARKET_PAYOUT` после сохранения подтверждённой выплаты. В payload передаются `sessionId`, `steamTokenId`, `sourceAmount`, `payoutAmount`, `payoutCurrency`, `withdrawalMethod`, `walletAddress`, `redBalanceOrderId`, необязательные `payoutId` и `payoutTxid`, а также `paidAt`; готового поля `text` нет. Telegram-бот добавляет обработчик этого типа и сам оформляет сообщение. Повторное событие с тем же `sessionId` не должно создавать второе сообщение; после получения события и после переподключения бот перечитывает заявку через Telegram API. Сайт читает состояние через web API и не подключается к Redis Stream. Полный контракт события и пример JSON: [уведомление о выплате](../patches/balance-market-payout-notification.md).
## Позиция в очереди

Пользовательские web и Telegram API возвращают `queueAhead` в `data` заявки при создании, чтении активной заявки и чтении заявки по ID. Поле есть только при `status=QUEUED`: `0` означает, что перед заявкой нет других; `1`, `2`, `3` — точное число заявок перед ней; `4` — перед ней больше трёх заявок. Число включает выполняемую заявку и ранее созданные заявки в очереди, срок ожидания которых ещё не истёк. После принятия заявки worker-ом `queueAhead=null`. Позиция может измениться при отмене, истечении срока или завершении других заявок, поэтому при обновлении экрана перечитывайте заявку с backend.

Тексты для интерфейса: `0` — «Ваша заявка следующая»; `1` — «Перед вами 1 заявка»; `2` — «Перед вами 2 заявки»; `3` — «Перед вами 3 заявки»; `4` — «Перед вами больше 3 заявок». При `null` строку очереди скрыть. Позиция не является оценкой времени: текущая заявка может ожидать ручного подтверждения выплаты. При `stage=WAITING_FOR_PAYOUT_APPROVAL` показывайте «Выплата ожидает проверки оператором», не кнопку подтверждения для клиента.

Web-маршруты: `POST /api/web/v1/balance-market/sessions`, `GET /api/web/v1/balance-market/sessions/active`, `GET /api/web/v1/balance-market/sessions/{id}`. Telegram-маршруты имеют тот же остаток пути после `/api/telegram/user/balance-market`. Например, для ожидающей заявки `data` содержит `{"sessionId":123,"status":"QUEUED","canCancel":true,"queueAhead":2,"queueExpiresAt":"..."}`; остальные поля DTO также присутствуют. Ручное подтверждение выплаты доступно только администратору через debug API и в клиентский интерфейс не выводится.
