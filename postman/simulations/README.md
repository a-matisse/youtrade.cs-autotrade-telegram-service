# Локальная проверка web-авторизации

Для ручной проверки запусти из корня `.\scripts\run-webapp.ps1 -Mock`.
Он запускает эту же имитацию вместе с Vite. Адреса экранов перечислены
в [руководстве webapp](../../webapp/README.md#локальный-запуск).

## Автоматизированная проверка

Из корня репозитория запустить имитацию backend:

```powershell
postman simulation run postman/simulations/web-auth.sim.yaml --port 4921 --no-history
```

В другом терминале собрать frontend и выполнить проверку:

```powershell
cd webapp
npm run build
cd ..
cd user-docs
npm run build
cd ..
node webapp/scripts/check-auth.mjs
```

Для проверки нужен установленный Playwright с Chromium. Если он находится вне
проекта, `PLAYWRIGHT_MODULE` задаёт путь к модулю, а
`PLAYWRIGHT_EXECUTABLE_PATH` — путь к исполняемому файлу Chromium.
Скрипт временно обслуживает собранный frontend на `http://127.0.0.1:4192`.
Для автоматической проверки нужен отдельный экземпляр имитации: тест сбрасывает
её состояние. Если ручной предпросмотр уже занял 4921, запусти вторую имитацию
с `--port 4922` и задай `$env:WEB_AUTH_MOCK_PORT = '4922'` перед запуском проверки.
Для проверки общей панели используется также сборка `user-docs/.vitepress/dist`.

Все API-запросы теста направлены в локальную имитацию. Внешние обращения
блокируются, публичные запросы к production URL перехватываются и также
обслуживаются имитацией. Пользователи, документы и credentials синтетические.
Проверяются вход и возврат, хранение access в памяти, cookie, перезагрузка,
согласование вкладок, истечение access, отсутствие автоматического повтора
записи, выход, потеря ответа refresh и независимость устройств.
Защищённые запросы проверяются на страницах документов и финансового кабинета.
Для кабинета используются синтетические ответы пяти маршрутов патча 8.
Дополнительно проверяются сохранение DOM панели при внутренних переходах,
тема между страницами и доменами, панель обучения и мобильное меню.
Проверка профиля использует отдельный Bearer GET `/api/web/v1/user/profile`
по актуальному web-auth: никнейм, отсутствие/ошибка фотографии, подписанный
относительный URL, однократное обновление после ошибки и перед истечением,
404/503 профиля без выхода из аккаунта, наведение, клавиатура и касание.
Учебная шапка ссылается на кабинет основного сайта и не запрашивает сессию.

`node webapp/scripts/check-startup.mjs` отдельно проверяет холодный запуск,
переход к странице, HTTP-кэш при reload и отсутствие загрузчика на внутренних
переходах. Этот сценарий работает без Postman, на порту 4194, без перехвата
запросов Playwright, чтобы сохранялся настоящий HTTP-кэш браузера.

Это проверка frontend по контракту. Настоящий Telegram OIDC, настройки
BotFather, подписи, state/PKCE, production HTTPS и конфигурация Nginx требуют
отдельной проверки с реальным backend. Границы проверки записаны в
[web-auth.context.yaml](web-auth.context.yaml).

После проверки остановить Postman через Ctrl+C. Не публиковать эту имитацию:
в ней намеренно предусмотрены служебные маршруты сброса и управления сессиями.
